## Суть изменения

Инверсия архитектуры ментора: было «детерминированная policy решает → LLM рендерит → отказ валидатора → шаблон». Становится: «модель с полным контекстом решает и говорит → детерминированные пост-проверки → отказ → одна починка → только потом шаблон». Мир, safety-стопы и governance источников не меняются.

## Что НЕ трогать (жёсткая граница)

- Движок пациента: `v25/engine.js` state transitions, `temporalPatientModel`, temporal_progression_rules, карточки кейсов и их значения.
- `parameterSafety.js` — safety-стоп параметров остаётся детерминированным и срабатывает ДО исполнения.
- Scoring: остаётся `formative_only`, numeric null.
- Privacy, gateway access control, rate limits (`openaiGateway.mjs` — кроме конфигурации задачи mentor, см. этап 1.6).
- Схема реплея — только аддитивные поля телеметрии.

## Этап 1 — ментор с полным контекстом

1.1. **Промпт.** `buildMentorPrompt` (`core/mentorAgent.js`): системный промпт собирается из файла `ONQOL_MENTOR_BEHAVIOR_SPEC.md` (читать файл, не пересказывать) + короткий блок жёстких границ: не подтверждать диагноз до дебрифа; числа только из allowlist; нераскрытые находки не упоминать; ноль или один вопрос за ход.
1.2. **Контекст.** В user-payload ментора добавить: полный транскрипт сессии (не только recent_dialogue), карточку кейса — revealed findings полностью, hidden findings в отдельной секции с пометкой `unrevealed: true, do_not_mention: true` (leak-детектор остаётся судьёй), все approved-правила, накопленное reasoning-состояние. Убрать mentor_policy как обязательный к исполнению — см. 1.3.
1.3. **Решение — у модели.** `classifyLearnerAdequacy` и `selectMentorPolicy` больше не диктуют mode/issue. Модель выбирает mode/issue/scaffolding сама по спеке. Policy продолжает вычисляться в shadow-режиме для телеметрии (0.2). В `validateMentorPayload` удалить проверки `policy_mode_mismatch`, `policy_issue_mismatch`, `policy_question_domain_mismatch`. **Сохранить**: `safety_interrupt_required` (при safety_critical issue режим обязан быть SAFETY_STOP) и `issue_not_in_brief` заменить на мягкую запись в телеметрию.
1.4. **Речь.** Убрать требование дословного цитирования revealed facts: пересказ свободен. Числовой контроль остаётся и усиливается: каждое число в реплике должно присутствовать в revealed facts, approved rules (включая dosing, этап 3) или в словах резидента этого/предыдущих ходов; иначе — reject `uncited_numeric_fact`.
1.5. **Гендер.** Удалить reject по `GENDERED_ADDRESS_RE`. Вместо этого: параметр сессии `learner_address_form` (не задан → нейтральные формы, инструкция в промпте) + автоопределение из собственных гендерных форм резидента в транскрипте («я сделала» → жен.). Регекс оставить как детектор для телеметрии, не для отказа.
1.6. **Длина и модель.** `MAX_MENTOR_CHARS`: 700 по умолчанию, 2000 для TEACH при scaffolding ≥3. `maxOutputTokens` mentor: 600 → 1600. `reasoning.effort` mentor: low → high. Модель ментора — сильнейшая доступная в конфиге (оставить конфигурируемой).
1.7. **Repair-loop.** При любом не-ok результате `validateMentorPayload`: ОДИН повторный вызов модели с текстом причины («реплика отклонена: uncited_numeric_fact — число 500 не найдено в источниках; исправь») и прежним контекстом. Только после второй неудачи — детерминированный шаблон. Логировать обе причины.

## Этап 2 — разговор и предусловия

2.1. **«Не распознано» умирает как ответ резиденту.** Если роутер не сопоставил концепт — ход всё равно уходит ментору (kind `clinical_reasoning`/`conversation_management`), и отвечает ментор живой репликой. Исполнение действий на пациенте — по-прежнему только через распознанные концепты и Case Card (роутер остаётся гейтом исполнения, не речи).
2.2. **Предусловия по всему транскрипту.** Блокирующее предусловие (согласие, оповещение анестезиолога, sign-in) считается закрытым, если соответствующее действие выражено в ЛЮБОМ предыдущем ходу (использовать operationalization-реестр и распознанные концепты, не совпадение фраз в одном ходе). Целевое поведение — ход 5 макета: «sign-in закрывается тем, что уже сделано».
2.3. **Реплики починки.** «я же написала», «я это уже сделала» и т.п. роутятся как ответ на контракт предыдущего вопроса ментора (pendingQuestion), не как новый нераспознанный ход.

## Этап 3 — dosing_rule и реестр не-EBM практик

3.1. **Новый тип правила** `dosing_rule` в `governance/clinicalGovernance.js` — схема в `BASE_RULES_V2_PROPOSAL.md` раздел 4. Runtime-эффект MENTOR_TEACHING только при `approved_for_training`; до подписи рецензента ментор отвечает «дозу сверь с формуляром» (текущее поведение — как переходное).
3.2. **Legacy-practice registry** (не-EBM, но частая практика: «литическая смесь» анальгин+димедрол+папаверин, метамизол соло, «голод-холод-покой» и т.п.): распознавание фраз резидента + связанное teaching-правило (что это, почему есть альтернативы с лучшей базой, что вместо). Записи создаются со статусом NEEDS_CLINICAL_REVIEW; контент вносит автор, НЕ выдумывать формулировки. Такие назначения не исполняются на пациенте как одобренные действия — они триггерят ментора.
3.3. Числовой контроль (1.4) расширить на dosing_rules как источник разрешённых чисел.
