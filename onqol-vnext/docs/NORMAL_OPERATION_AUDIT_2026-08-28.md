# ON QOL vNext — аудит нормальной работы

Дата: 2026-08-28  
Объём: APP-004, оба режима больницы, learner-facing RU route, clinical governance, privacy, server/deployment и эксплуатация.

## Короткий вывод

Техническое ядро работает устойчиво, но продукт пока нельзя давать ординаторам как клинически надёжный тренажёр. Сейчас это хороший внутренний симулятор механики: он хранит события, воспроизводит кейс по seed, различает ограничения больницы и платформы, принимает многие действия и строит debrief. Главная проблема не в падениях приложения, а в том, что медицина почти полностью находится ниже статуса `approved_for_training`: пациент не развивается во времени, лечение не меняет состояние, опасные решения почти не останавливаются, а клиническая готовность к выписке не проверяется.

## Что исправлено по сессии пользователя

- `опрос и посмотреть живот` выполняет два действия, а не только осмотр;
- `опрос пациента` распознаётся так же, как `опрошу пациента`;
- вопросы о уже смоделированных фактах, например `рвота была?`, получают ответ пациента;
- `получить результаты` и вариант с опечаткой `получить резульатты` двигают часы до ближайшего запланированного результата;
- сложный заказ не теряет биохимические показатели, если в том же фрагменте указан СРБ;
- неподдержанная часть заказа, например `ОМТ`, больше не исчезает молча;
- добавлены пять регрессионных тестов по реальной сессии.

## Клинические препятствия

### Критические

1. **Клинический контент не одобрен.** Для APP-004 одобрено 0 из 11 объектов, создающих patient truth, и 0 из 6 клинических правил. Сгенерированный пациент используется только как development content.
2. **Пациент не меняется от времени.** Согласованной модели естественного течения нет. Часы идут, но боль, температура, гемодинамика и воспалительные показатели не развиваются.
3. **Лечение не даёт эффекта.** Препарат или инфузия записываются как выполненные, однако состояние пациента не меняется: дозы и response envelopes не прошли review.
4. **Нет работающей safety net.** Одобренных Level 3/4 правил нет. Опасная доза или решение могут быть приняты системой без клинического предупреждения.
5. **Нет deterioration и осложнений.** События и каркас существуют, но ни один одобренный механизм их не создаёт. Ошибки и задержки поэтому почти не имеют последствий.
6. **Небезопасная логика выписки.** Клинические критерии выписки pending; после структурного прохождения маршрута пациент может быть выписан без реальной проверки боли, переносимости жидкости и общего восстановления.

### Существенные

- антибиотикопрофилактика фиксируется, но правильность препарата, дозы и времени никем не подтверждена;
- aspiration risk и анестезиологические решения не завершены;
- репродуктивные риски существуют в patient truth, но полноценный диагностический маршрут и правила ещё не утверждены;
- болезнь пока одна — аппендицит; варианты APP-001–APP-005 мигрированы из V3.5 в контролируемый каталог, но learner-facing остаётся только development-кейс APP-004, APP-001–003 ожидают review, а APP-005 оставлен faculty preview;
- послеоперационное восстановление, мониторинг и осложнения почти не моделируются;
- профили реальных больниц Казахстана имеют `pending_owner_review`, а данные о компонентах крови не заданы.

## Технические и продуктовые препятствия

### Высокий приоритет

1. **Интерпретатор остаётся словарным.** Теперь он честно сообщает о непонятой части, но новые формулировки и опечатки всё ещё требуют ручного добавления. Live provider-backed interpreter в приложение не подключён.
2. **Клинические языки не локализованы.** Переключатели ҚАЗ/ENG меняют оболочку, но пациент, наставник, команды и clinical content остаются русскими. Для пользователя кнопки создают ложное ожидание полноценной локализации.
3. **Нет сохранения сессии.** Состояние живёт только в React memory; обновление страницы уничтожает кейс. Аккаунт и восстановление сессии отсутствуют.
4. **Нет production deployment path.** `vite build` создаёт статику, а gateway подключён только к dev server. Нет hosting-конфигурации, production server, release gate или CI evidence для развёрнутой версии.
5. **Экспорт требует privacy-решения.** JSON содержит raw learner text, полный state и hidden truth. В интерфейсе нет предупреждения не вводить сведения реального пациента; политика хранения vNext не мигрирована.

### Средний приоритет

- reasoning-state теперь хранит формулировки рабочего диагноза и дифференциального ряда, но production interpreter path для автоматического извлечения этих данных ещё не мигрирован;
- немедленные процедуры вроде назогастрального зонда не реализованы;
- отказ пациента от вмешательства объявлен в state/event model, но не может произойти;
- обычные осмотр, анамнез и назначение занимают ноль минут; добавлено явное ожидание, но модель длительности действий остаётся неполной;
- диагностические статусы `in_progress`, `delayed`, `cancelled` объявлены, но почти не создаются;
- пациент не перемещается в radiology: визуализация выполняется при формальном нахождении в приёмном покое;
- динамические ограничения ресурсов не восстанавливаются во время кейса;
- нет dev diagnostics panel и автоматического браузерного теста в `npm run verify`;
- content build проверяет provenance, но не все cross-file references.

## Безопасность и эксплуатация

- `npm audit --omit=dev`: 0 известных уязвимостей на 2026-08-28;
- API key находится только на server side, запросы имеют timeout и `store: false`;
- если gateway будет включён публично, его нужно усилить: обязательный allowed origin, аутентификация сессии/pilot token, ограничение размера body, устойчивый rate limit и безопасные ошибки без provider detail;
- полный `npm run verify` прошёл после governance и Wave 1: content check, 241/241 tests, lint и production build;
- ручной browser smoke прошёл без console errors: опрос + живот, focused-вопрос, сложный заказ, предупреждение об `ОМТ` и переход времени к результату.

## Рекомендуемый порядок работ

1. Не выпускать тренажёр для клинического обучения; сохранить статус **NO-GO**.
2. Провести review и approval patient truth, natural course, treatment effects, safety rules и discharge criteria.
3. После клинического review включить deterioration, последствия лечения и осложнения — только из одобренного content.
4. Закрыть технические learner blockers: reasoning capture, procedures, persistence, honest locale gating и browser E2E.
5. Затем подготовить privacy notice, production server/deployment, auth/rate limits и формальный release gate.
