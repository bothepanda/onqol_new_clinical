# Stateful Grounded Mentor — Wave A (appendicitis slice)

**Status: implemented behind `STATEFUL_GROUNDED_MENTOR_V1` (default off). Flag-off behavior unchanged (lint/build/637 pre-wave tests pass unmodified; see Verification). Not yet measured against a live provider.**

## 1. What this wave was for

Before this wave, onqol-vnext had two mentor systems that never spoke to each other: the deterministic `mentorEngine.js` (wired into the real clinical turn path, `submitLearnerTurn.js`) and an experimental, unmerged LLM channel (`groundedDialogue.js` + `mentorGateway.mjs` + `unifiedChat.js`) that only fired for "discussion" turns routed *around* `submitLearnerTurn`. This wave makes the mentor that speaks during a normal clinical turn use grounded, learner-anchored wording — generated by an LLM but structurally unable to invent a clinical fact — while every safety decision, issue detection, and scaffolding level stays exactly as deterministic as before.

Scoped to one content slice (`APP-004`, appendicitis — the only bundle that exists) per the plan's own suggested rollout: Wave A (this one) → Wave B (fluids-01 + approved-card migration) → Wave C (other surgical cases).

## 2. Architecture

```
Learner message
  -> vNext Language Interpreter (unchanged)
  -> submitLearnerTurn.js: commands executed, events recorded (unchanged)
  -> mentorEngine.decideMentorResponse (unchanged): mode, issue, safety, scaffold rung
  -> [flag on] mentorAdequacy.classifyAdequacy + mentorMemory.advanceMentorMemory:
       SUFFICIENT/PARTIAL/VAGUE/STUCK/EVASIVE/UNSAFE, working-memory update
  -> recordMentorIntervention: MENTOR_INTERVENED event (deterministic text + memory fields)
  -> [flag on, async, useSession.js] renderMentorResponse.js
       -> mentorBrief.js: hidden-truth-free structured brief
       -> cardRetrieval.js: bounded, issue-scoped approved-card subset
       -> statefulGroundedMentor.js -> groundedDialogue.js: propose, verify,
          one bounded regeneration, else fall back to the deterministic text
       -> recordGroundedMentorResponse: MENTOR_GROUNDED_RESPONSE_RENDERED
          (non-authoritative - display/audit only)
  -> learner-facing response
```

`mentorEngine.js` is untouched except one line (the STUCK branch now prefers `state.mentor.pendingMentorQuestion.issueId`, which survives a turn boundary, over the old `state.mentor.openQuestion.issueId`, which doesn't — see §5). It still owns every decision the ТЗ's §5 allows a deterministic engine: safety candidate, teaching candidate, current-issue detection, hard safety rules, whether to intervene at all. It is no longer the source of the *live* learner-facing sentence when the flag is on and a grounded alternative was accepted — but its sentence is always what gets recorded in the domain event log, and always the fallback when grounding fails twice.

## 3. New state: `state.mentor`'s working memory

Four additive fields, all `null`/`0`/`[]` and never read when the flag is off:

- `pendingMentorQuestion` — `{issueId, askedTurn, learnerQuote, expectedAnswerDomains, scaffoldingLevel}`. Unlike `openQuestion`, it survives `LEARNER_TURN_RECEIVED`, so a short reply two or more turns later still resolves against it.
- `probingStreak` — consecutive non-SUFFICIENT verdicts on the current pending issue. Past 4 (matching the scaffold ladder's own 4 rungs), the issue is deferred rather than re-probed a fifth time.
- `recentMentorQuestions` — last 3 `{issueId, prompt}`, by deterministic prompt (not the eventual LLM wording, which is async and comes later) — this is what a "don't repeat an identical question" check compares against.
- `deferredMentorIssues` — issue ids pushed here instead of re-asked; a debrief surface for these is a Wave B/C item, not built this wave.

## 5. The bug this wave found in its own review

`state.mentor.openQuestion` is cleared on every `LEARNER_TURN_RECEIVED` by design (a question must not outlive the turn that answered it). `mentorEngine.js`'s STUCK branch used to read `state.mentor.openQuestion?.issueId ?? "generic"` to decide which issue a "не знаю" continues — which meant a "не знаю" **one full turn after** the question that provoked it would already see `openQuestion` as null and silently fall back to a "generic" issue, breaking probing-streak continuity exactly where the ТЗ's §8/§9 care most. Fixed by preferring `pendingMentorQuestion.issueId` (which survives the turn boundary) when present; `statefulGroundedMentor.behavioral.test.js`'s B02b pins it.
